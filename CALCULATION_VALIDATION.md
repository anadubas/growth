# Calculation validation findings

Results of cross-validating this application's growth calculations against the
WHO's own reference implementation, the
[`anthro`](https://github.com/WorldHealthOrganization/anthro) R package
(version 1.1.0.9000, validated from a local checkout).

The validation harness lives in `test/growth/anthro_cross_validation_test.exs`,
with the golden fixture generated by `test/fixtures/generate_anthro_golden.R`
(`task fixture:anthro`). Each fixture row is asserted twice:

1. **Formula equivalence** — `Growth.Zscore.calculate/4` fed with WHO
   day-table LMS values must reproduce the reference z-score (tolerance 0.011,
   which is only R's 2-decimal rounding).
2. **End-to-end pipeline** — `Growth.Calculate.calculate_result/3` using the
   app's own tables, age derivation and lookups (tolerance 0.15).

All 1440 fixture rows pass on both levels.

Beyond the automated suite, two additional probes were run while writing this
document (not part of the test suite):

* a provenance check of the 5–10 years `weight_for_age.csv` rows, and
* a mid-month precision probe, described in finding 3.

## Findings

### 1. LMS formula: exact match with the WHO reference — no action

1440/1440 rows agree within 0.011, covering both the raw LMS computation and
the WHO adjustment for values beyond ±3 SD. `Growth.Zscore.calculate/4` is
mathematically equivalent to the reference implementation.

### 2. Reference tables and lookup: faithful for months 0–59 — no action

Every key the app can query (`{gender, :month}` for months 0–59, both sexes,
all four indicators) was exercised at month-boundary ages, with a maximum
drift of 0.043 (weight, day 31). No transcription errors, wrong-source rows or
off-by-one lookups were found.

The suspicious source filename in `weight_for_age.csv` for ages 5–10
(`hfa-girls-z-who-2007-exp_….xlsx` — a height-for-age file name) was checked
and contains genuine weight-for-age WHO 2007 data (girls, month 61: median
18.26 kg, matching the published standard). The label is wrong, not the data —
see finding 8.

### 3. Month-granularity bias in early infancy — action recommended

The app resolves reference rows by whole months (`floor(days / 30.4375)`),
while the WHO curves are day-precision. A child measured mid-month is compared
against the month-*start* median, which is smaller, so z-scores are
systematically inflated in the first months of life.

Measured probe: for children sitting exactly on the WHO day-precision median
(true z = 0.00), the app reports:

| age (days) | weight | height | head circ |
|---|---|---|---|
| 8 | +0.32 | +0.74 | +0.64 |
| 15 | +0.84 | +1.36 | +1.20 |
| 45 | +0.86 | +0.93 | +0.80 |
| 100–200 | +0.23 | +0.38 | +0.29 |
| 400+ | ≤0.10 | ≤0.17 | ≤0.06 |

A two-week-old at the true median reads as roughly the 92nd height percentile.
The bias decays to noise (~±0.1–0.2) after the first year. BMI is largely
unaffected (≤0.57 worst case, day 45).

This is a design property, not a bug — the fixture deliberately aligns the two
implementations at month boundaries so correctness is measured separately from
this precision gap.

**Suggested actions:**

- [ ] Wire the week tables for children under 91 days: WHO 0–13-week rows are
      already shipped in `priv/indicators/*.csv` and loaded into ETS (keyed
      `{gender, :week, age}`), but `Growth.LoadReference.get_reference/3` only
      ever queries `:month` keys. Looking up `:week` keys first for ages
      < 91 days collapses the worst-case bias (~1.4 z) to the same level as
      every other age.
- [ ] Document the month-granularity limitation in the README, next to the
      validation section.

### 4. Ages ≥ 60 months are unvalidated — accept and document

The WHO Child Growth Standards (and the `anthro` package) cover 0–60 months.
Above 5 years the app uses the WHO 2007 reference, for which no equivalent
cross-validation exists in this repository. Those tables are correct by
provenance only (downloaded WHO spreadsheets), plus the spot check described in
finding 2.

**Suggested actions:**

- [ ] State in the README that the 5+ years tables are not covered by the
      cross-validation.

### 5. Behavior at exactly 60 months is undefined — decide a policy

The reference implementation returns NA from 60 months on
(`age_in_months < 60` validity rule). The app still has a month-60 row and
will happily compute a z-score. Harmless, but worth an explicit decision.

**Suggested actions:**

- [ ] Decide whether month 60 should return results (current behavior) or be
      treated as out of domain like the reference implementation, and encode
      it in `Growth.LoadReference` or `Growth.Calculate` with a test.

### 6. Degenerate inputs are not handled — add guards

The reference implementation maps invalid measurements to NA (measure ≤ 0, NA
inputs, out-of-domain ages). The app has partial coverage:
`calculate_result/3` returns an unavailable result for non-numeric measures,
but `Growth.Zscore.calculate/4` with measure ≤ 0 feeds negative or zero values
into `:math.pow`, which can raise `ArithmeticError` (negative base with
non-integer exponent) or return NaN.

**Suggested actions:**

- [ ] Return an unavailable/NA-equivalent result for measure ≤ 0 (matching the
      reference behavior), with tests for 0, negative and nil measures.

### 7. The `l == 0` branch in `Growth.Zscore` is dead code — keep or test

No WHO table row has `l = 0`, so the log-transform branch never runs in
production. It is either kept as mathematical completeness or removed.

**Suggested actions:**

- [ ] Either delete the branch or keep it and add a unit test pinning its
      behavior (`log(measure/m) / s`), so it is not silently broken.

### 8. Provenance hygiene in `priv/indicators/*.csv` — cosmetic

* `weight_for_age.csv` ages 5–10 point at `height-for-age-(5-19-years)`
  URLs; the data is right (finding 2), the URLs are not.
* `bmi_for_age.csv` and `height_for_age.csv` contain duplicate month-24 rows
  (from the 0–2 and 2–5 sources). ETS last-write-wins makes this benign today
  (both rows are the same standard), but it is fragile.

**Suggested actions:**

- [ ] Fix the mislabeled source URLs in `weight_for_age.csv`.
- [ ] Deduplicate the overlapping month rows (or add a loader warning when a
      key is overwritten).

### 9. Percentile, classification and SD cutoff columns are untested — low risk, cheap to close

`Growth.Percentile.calculate/1` (Φ(z) via `:math.erf`), `Growth.Classify`
cutoffs (WHO/SISVAN conventions) and the displayed `sd0..sd3` columns were not
part of the cross-validation. Spot checks agree with textbook values and WHO
cutoffs.

**Suggested actions:**

- [ ] Add table-style tests for `Growth.Classify` covering every boundary
      (z = -3, -2, 1, 2, 3 on both sides) per indicator.
- [ ] Assert the app's `sd*` columns against the LMS-derived cutoffs
      `m * (1 + l * s * sd)^(1 / l)` within ~0.2 (the WHO spreadsheets round
      them to 1 decimal), reusing the existing fixture infrastructure.

## Reproducing the numbers

```bash
# golden fixture + cross-validation suite (requires R only for regeneration)
task fixture:anthro
mix test test/growth/anthro_cross_validation_test.exs

# mid-month bias probe: children exactly at the WHO day-median (true z = 0)
# 1. emit day-table medians with R (see test/fixtures/generate_anthro_golden.R
#    for how to source the anthro implementation)
# 2. run them through the app pipeline and compare
```
